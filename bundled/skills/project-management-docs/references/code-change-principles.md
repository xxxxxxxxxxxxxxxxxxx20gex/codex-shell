# 代码修改原则

用于开发项目的 AGENTS.md。保留以下八条的语义；父级已完整覆盖时继承，不重复维护。项目特有的工具、命令和边界另行补充。

1. **先理解，再修改。** 根据任务风险阅读相关实现、调用方、测试和项目约定，确认当前行为、目标行为和影响范围。区分事实与假设；能从现有证据判断的问题自行处理，只有在不同解释会明显影响功能、兼容性或实现方向时才询问。
2. **做最小充分实现。** 只实现当前明确需求，不为假想的未来需求预留抽象、配置层或扩展点。“最小”指满足正确性、必要安全性和既有契约下的最低总成本，不是单纯追求改动行数最少。
3. **控制改动范围，允许必要重构。** 不修改与当前需求无关的命名、格式、类型、文件结构或实现风格。现有结构若直接妨碍正确实现、必要验证或造成同一业务规则必须多处同步修改，可以进行最小范围的局部重构，并说明原因。
4. **保护既有行为和契约。** 未被需求明确改变的行为应保持稳定。修改公开接口、数据格式、配置项、数据库结构或错误语义时，检查相关调用方和兼容性影响。仓库内没有引用，不代表外部没有依赖；需要破坏性变更时，应明确影响和迁移要求。
5. **按业务语义决定抽象。** 清晰的代码优于聪明的抽象。单次使用且逻辑简单的流程默认内联；只有存在明确复用、稳定业务语义、共同变化原因、复杂度隔离或系统边界时才提取函数、类或模块。不要机械依据重复次数决定是否抽象，也不要为了形式上的结构化拆出大量只调用一次的小函数。
6. **在真实边界进行校验，诚实处理错误。** 对用户输入、外部接口、文件和网络、状态转换及关键不变量进行必要校验。对已有明确契约保证的内部条件，不重复添加无意义的 null check、类型断言或 fallback。能够恢复时才恢复，否则按项目约定传递清晰错误；禁止吞掉异常、伪造默认结果或掩盖失败。
7. **保持代码和改动干净。** 删除本次改动产生的无用 import、变量、函数、配置和分支；与当前需求无关的既有死代码不擅自清理。注释只解释代码无法直接表达的原因、约束或 workaround，不重复描述实现。同步更新受本次改动影响的必要文档。
8. **以可验证目标收尾。** 修改前明确完成条件，修改后运行与风险匹配的测试、类型检查、lint、构建或最小复现。修复缺陷时验证原问题已复现且已解决；新增行为时验证关键成功和失败路径。准确报告已验证内容、未验证内容及剩余限制。原则冲突时，优先保证正确性、必要安全性和明确契约，其次控制范围和维护成本。
